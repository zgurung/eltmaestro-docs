    Architecture¶

    ELTMaestro is a metadata-driven ELT/data-integration platform. A Windows WPF client lets users build pipelines visually; those pipelines are persisted as job XML in a PostgreSQL audit/metadata database and executed by a Java batch engine that pushes work into cloud data warehouses (Snowflake, Redshift, Synapse, ClickHouse, Greenplum, Netezza, Yellowbrick, Databricks, Spark, ...).

    This doc is the one-pager for newcomers: what each piece is, how they connect, what's changed recently. Each component has its own deep-dive file linked from the table.

    The pieces¶

    Component Subdir Stack Role
    WPF client source/root-win-client/ .NET / WPF / XAML (Windows) The visual designer + operator UI. Users build jobs, browse metadata, run/monitor batches. Talks to the meta-service over SOAP. Out of scope for this doc set today — its docs will land here later.
    Meta-service source/root-engine-service/MaestroMetaDataProviderService/ Spring Boot 3.3.5 + Java 21 + embedded Jetty 12 + Eclipse Metro 4 (JAX-WS RI) Single @WebService class (MaestroMeta, ~5,000 lines, ~165 SOAP operations — every public method is exposed in JAX-WS implicit mode). Handles authentication, metadata CRUD, admin commands, audit, file fetches. See SERVICE.md.
    Batch engine source/root-engine-core/ Java 21 + Spark 4.1.1 + Scala 2.13 Reads job XML, builds a step DAG, launches each step as a thread, drives them to completion. Each step is a BaseStep subclass; the catalog is wired through StepProvider. See ENGINE.md.
    Shared lib source/root-engine-shared/ Java 21 A tiny module that holds the two org.maestro.share.* classes safely shareable between engine + service (Crypt, MaestroCompressor). The rest of share/ is deliberately duplicated. See SHARED.md.
    Install + deploy source/root-engine-install/ Bash / SQL / Dockerfile One source of truth for both Docker image build (via the Dockerfile) and portable bare-metal install (via install.sh). Holds initdb.sql, metadata seeds, migrations, JDBC driver list, admin commands (mstart-*, mstop-*), entrypoint scripts. See INSTALL.md for the operator view; the dev view lives in this file.
    Audit / metadata DB source/root-engine-install/db/initdb.sql PostgreSQL 16 The sqlmaestro control-plane DB — 83 tables + 30 views holding the catalog (jobs, connections, control tests, config; owned by the meta-service) and the execution record (runs, per-step status, logs, metrics; written by the engine). Job definitions themselves are XML files on disk, not rows. See DATA-MODEL.md and the column-level DATA-MODEL-SPINE.md.
    CI source/Jenkinsfile Declarative Jenkins pipeline Builds both Java artifacts, builds + pushes the Docker image, optionally deploys, prunes the registry, publishes installer tarballs. See CI-CD.md.
    Reactor pom source/pom.xml Maven aggregator Builds engine-shared → engine-core + service in dependency order from source/. Added 2026-05-26 to remove the manual mvn install ../root-engine-shared first footgun.

    Data flow at runtime¶

                              .--- WPF client (Windows) ---.
                          |                            |
                          | designer / operator UI     |
                          '-----------+----------------'
                                      | SOAP/HTTPS  (port 8181)
                                      |   WSDL @ /MaestroMetaDataProviderService/MaestroMetaService
                                      v
                          .--- Spring Boot meta-service (Linux/Docker or bare metal) ---.
                          |  - authenticates users (t_user)                              |
                          |  - reads/writes job XML, connections, metadata               |
                          |  - shells out to admin scripts (Runtime.exec)                |
                          |  - audit (auditPerformanceMetricsStart/Stop)                 |
                          '---------+----------------------+---------------------------'
                                    | JDBC                 | spawns (mstart-*) / fork+exec
                                    v                      v
                          .--- PostgreSQL ---.   .--- Engine batches (sqlm.jar, per-job JVM) ---.
                          |  sqlmaestro DB    |   |  RunBatch.main(--batch job.xml ...)         |
                          |  ~109 tables      |<--+  reads jobs/connections/watermarks via JDBC  |
                          |  audit + meta     |   |  builds step DAG, launches step threads      |
                          '-------------------'   |  pushes work into target warehouses          |
                                                  '-+--------+-----------+----------------------'
                                                    |        |           |
                                                    v        v           v
                                              Snowflake  Redshift   ClickHouse  ... (any target with a JDBC driver,
                                                                                     or S3 / Azure Blob via SDK)

    Two distinct JVMs at runtime:

    • Long-running: the Spring Boot meta-service (one process, serves SOAP).
    • Short-lived per batch: each batch run is its own java -jar sqlm.jar --batch ... invocation, spawned by mstart-* admin scripts that the meta-service calls via Runtime.exec. The engine doesn't run inside the service JVM.

    Things that look like they were touched but stayed:

    • The isCDC / $QUERY_CDC_DELETE / $QUERY_CDC_INSERT pattern in the engine is not LogMiner CDC. Despite the name, it's the engine's generic upsert primitive (delete-then-insert by key), used by SCD1/SCD2/Table/Onstage merge. Preserved.
    • The Helper, JdbcConnection, JdbcConnectionManager, JdbcConnectionTracker, PG files in org.maestro.share.* are still duplicated between engine and service. Heavy drift (thousands of lines) between batch-runtime and SOAP-runtime needs; unifying would mean rewriting both sides to agree. See SHARED.md for the audit numbers.

    Where state lives¶

    State Location Lifecycle
    Job definitions t_job_meta etc. in sqlmaestro Postgres Persisted across upgrades. Edited via the WPF client; consumed by the engine.
    Job XML (per-run material) Written under data/workflow/ by the meta-service before each RunBatch Recreated each run.
    Audit / batch run history sqlmaestro Postgres Persisted across upgrades.
    Connection definitions t_jdbc etc. in sqlmaestro Persisted.
    Watermarks (incremental loads) t_high_watermark etc. Persisted. Read/written by the engine.
    Halt files EngineState.haltFile on disk under the install dir Per-run; created to terminate a running batch.
    Container volumes (Docker deploy) pgdata (audit DB), hdfs (Spark warehouse), data (workflows + logs) Named docker volumes. Survive container restarts; wiped only on DESTRUCTIVE=true deploys.
    Bare-metal layout /data/iserver/ (see OPERATIONS.md for the full tree) Audit DB + workflows + keystore preserved across upgrades; binaries and pgsql.factory/ are replaced.

    Cross-side mirroring (the duplication tax)¶

    The five org.maestro.share.* files (Helper, JdbcConnection, JdbcConnectionManager, JdbcConnectionTracker, PG) are duplicated between the engine and the service. The drift is intentional — the service has SOAP-runtime concerns (audit metrics, token validation, table-maintenance methods) the engine doesn't, and the engine has batch-runtime concerns (BaseStep-typed signatures, dialect templates, script execution) the service doesn't.

    Implication for any change to those five files: check whether the same code path exists on the other side and whether the same fix is needed there too. SHARED.md has the full audit (LOC drift, javap public-API comparison, side-by-side behavioral examples) and a checklist for bug-fix mirroring.

    Crypt and MaestroCompressor are the only share/ classes actually shared via the engine-shared Maven module. Everything else is paid duplicates.

    "Where do I add my change?"¶

    Goal Subdir Key file
    New job/step type source/root-engine-core/src/main/java/org/maestro/engine/steps/... Register in StepProvider.getBaseStep(...)
    New SOAP method source/root-engine-service/.../MaestroMeta.java Add a public method on MaestroMeta; Metro picks it up at startup
    New cloud-warehouse target engine/steps/<backend>/core/ + pipeline/core/JdbcTarget<Backend>.java Cross-reference an existing backend
    Bug fix in shared Helper.java / PG.java / JdbcConnection.java Both engine + service copies (they're duplicated; see SHARED.md) —
    New environment variable read at runtime Engine: Helper.getEnvironmentValue("X"). Service: same Helper plus a MaestroLifecycle hook if it needs init-time setup. —
    New admin command source/root-engine-install/admin.commands/mfoo + register on PATH via env_integrator —
    New DB schema change source/root-engine-install/db/migrations/NNNN_description.sql Tracked in schema_version; applied by both Docker entrypoint and bare-metal update-server.sh. Never edit a migration that's already shipped.
    New JDBC driver source/root-engine-install/jdbc_list.json (URL + filename); fetch-jdbc-drivers.sh downloads it at build time —
    Adjust the Docker image build source/root-engine-install/docker/Dockerfile —
    Adjust the Jenkins pipeline source/Jenkinsfile —
